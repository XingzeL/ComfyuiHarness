# 工作流管理规则

按当前 ComfyUIAPI 的模块方式组织工作流。HarnessUI 提炼模块搭建方法与模板，不强制所有工作流适配同一个运行器，也不新增自动加载专用适配器的机制。

## 一个工作流一个模块

模块放在 `workflows/<名称>/`，按实际需要包含：

```text
api.py                   编程调用入口
run.py                   命令行入口
models.py                本工作流配置模型
workflow_builder.py      配置到工作流节点的转换
comfy_client.py           ComfyUI 通信
output_paths.py           本模块输出目录规则
workflow.json            运行使用的 API 图
config.example.json      配置示例
README.md                用途、依赖、参数、输出及恢复说明
runs/                    任务脚本及长期复用示例
output/YYYYMMDD/         成图
output/jobs/<run_id>/    任务参数、提交图和 manifest
```

节点映射、LoRA 接法、派生参数、输入缩放和特殊输出由本模块的 models / workflow_builder / api 明确实现。文件数按实际需要，不为无需求的环节建立空代码。不靠自动扫描 Python 文件运行插件。

已有的 basic-t2i 与 basic-t2i-lora 是公共运行器参考样例，不是新增工作流必须采用的架构。`workflow.spec.json` 仅属于这套参考运行器。

## 保存方式跟随工作流

保留来源工作流实际使用的保存节点，不为了迁移强制改成标准 SaveImage。

- 原项目多数模块使用 `Image Save`，由 API 在提交前设置本模块 `output/YYYYMMDD/` 和唯一 filename_prefix，ComfyUI 在后台直接写盘。目标服务必须能访问配置的输出路径。
- 标准 SaveImage 也保留，例如原项目 UpscaleAnima2.9。它保存到 ComfyUI 输出目录，提交时记录 save_image_prefix；后续按该模块说明查历史或收集，不把预测编号当成确定文件名。
- 每个模块 README 必须写明保存节点、实际输出位置、覆盖行为、预期路径可信程度，以及是否需要后续归档。

唯一输出名使用模块名、run_id、时间、序号等技术信息，不带图像内容。重试使用新前缀，不覆盖原结果。

## 异步投递

按原项目约定：预检通过后，构建 prompt、提交 /prompt，返回 prompt_id、种子、预期路径或保存前缀，并结束投递轮。投递轮不轮询、不等待成图、不复制本轮结果。

成图由 ComfyUI 后台写盘。用户要求等待、检查结果，或在后续轮次中，再确认执行状态、检查黑图与损坏、汇总或归档。预期路径不是完成证据；入队成功不等于成图成功。

投递前检查服务就绪及最近输出是否异常。需要重启时按本机已配置的服务管理方式操作，先检查队列及影响；具体工作流的重启要求记录在其 README 中，不成为公共客户端的隐式动作。

正式生成前还要检查本机 limits.max_image_pixels，未确定时提醒用户并暂停，超限不能直接入队；多阶段尺寸须由当前模块检查。详见 [环境配置规则](environment-and-files.md)。

服务功能入口固定在 scripts，见 [本机脚本说明](../scripts/README.md)。黑图按 [任务规则](tasks.md) 最多三次恢复重启；输入及结果汇总遵守 [原项目式输出与汇报](reporting.md)。

## 每个工作流自己的运行规则

统一写在本模块 `README.md` 的「运行规则」节。Agent 选择工作流后、构建或投递前必须阅读这一节；不要求所有工作流采用相同的启动、重启、串行或等待策略。

该节只需说明：

- 何时做：投递前、每张之间、执行成功后、失败时，还是整个批次结束后。明确频率。
- 做什么：重启、预检、清理特定缓存或其他必要操作，写清顺序与依据。
- 谁来做：本模块 api.py、run.py 或 runs 下的结果检查脚本；不能只写在文档却无人执行。
- 调用什么：本机配置指向的服务脚本、解释器或命令，不写死原电脑路径。
- 何时可以做：例如队列为空、没有其他任务，以及操作影响范围；禁止强行清队列来满足条件。
- 不满足时怎么办：能力未配置或操作失败时停止本次投递并报告；已明确为必需的步骤不能静默跳过。记录执行结果及停止条件。

**入队返回不等于运行完成。** 要求“执行完成后重启”时，不能在异步 API 收到 prompt_id 后立即重启，否则会中断刚提交的任务。完成后动作须由后续检查脚本或明确配置的完成处理程序，在确认任务结束及服务可操作后执行。尚未实现执行者时标为未实现。

如果目标只是保证相邻两张之间重启，可以明确采用原项目 text2imgAnima 的形式：每次投递前检查队列影响，再执行 restart → preflight → 投递一张。原模块实际重启发生在入队前，不应误写成入队后或执行完成后。

规则写在 README，执行逻辑留在模块自己的 API/脚本，机器命令放在本机配置和服务脚本。这些要求不需要新增全局适配器或通用调度器。

每次任务先查看当前基底的角色 LoRA，默认加载匹配目标角色的可用 LoRA；档案不要求按工作流保存不同配方，Agent 每次自行适配。换角先由 LLM 看图分析 tag，再结合 WD14 和用户要求规划过滤及补充，见 [LoRA 管理准则](lora-management.md)。

## 可移植性与记录

机器地址和 ComfyUI 路径来自本机环境配置。资源引用使用本机可识别的相对名称及资源登记；不复制原电脑绝对路径、凭据、任务内容或特定节点编号到通用规则。

保留各工作流自己的节点与依赖要求，目标电脑缺少时明确报告并按授权补齐，不假装模块已能运行。

已确认的参数和 manifest 保留规则继续执行：本包保留复现与恢复依据，临时脚本单独清理。这里沿用原项目的工作流封装、投递与保存方式，不恢复会破坏历史依据的广泛删除操作。

## 搭建入口

复制 `templates/workflow_module/` 到 `workflows/<名称>/`，替换为目标机器的 API 图，调整 models、workflow_builder 与 README，填写本机环境配置，再进行 dry-run、依赖核对和真实环境验证。

模板演示 SDXL + Image Save 的逐模块封装，未在真实 GPU 上验证。选择其他模型或保存节点时改该模块，不要求修改公共运行器。目录中的 runs/output 容器可在初始化时创建；模板中的 Python 代码是可测试示例，不是假成功占位脚本。
