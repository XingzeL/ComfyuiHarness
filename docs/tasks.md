# 任务生命周期与验证

逐模块工作流的投递和保存以 [工作流管理规则](workflows.md) 及各模块 README 为准：异步投递后由原保存节点写盘，后续检查。以下五命令和 collection_status 是公共参考运行器的具体实现，不要求直接落盘的模块再通过 collect 才能归档。

本文的黑图恢复规则适用于所有工作流，结果汇总和汇报遵守 [输出与汇报规则](reporting.md)。

通用操作入口预留在 scripts/preflight_submit.py、check_outputs.py 和 collect_outputs.py，当前均待实现；本机 Agent 可对接本模块已有代码，不要求另建一套运行器。不能把占位入口当作预检或结果检查已经完成。

## 从构建到成图

1. `build`：离线读取图和资源登记，展开默认参数，生成具体种子，验证映射与基本图结构。仅输出 JSON，不创建 run。
2. `inspect --task`：读取服务端节点定义，检查所需节点、必填输入、连接类型、枚举和基础数值边界。不检查权重语义或 GPU 可执行性。
3. `submit`：重新构建、保存记录、在线检查、快照并上传输入、保存实际 prompt、提交一次。立即返回，不轮询、不自动重试。
4. `status`：根据该任务原服务地址查询历史与队列；没有历史且不在队列时是 `unknown`，不是成功。
5. `collect`：确认执行成功后，读取声明输出节点的实际 `images`，通过 `/view` 下载到独立目录，解码并记录尺寸、亮度与摘要。

每次 build 都会为未指定种子的任务分配新种子。希望 inspect、submit 与预览一致时，在任务配置中显式填写种子；不要认为上次 build 的随机值会自动沿用。

## 状态含义

`execution_status`：`prepared`、`submitting`、`submitted`、`queued`、`running`、`succeeded`、`failed`、`submit_failed`、`submission_unknown` 或 `unknown`。

`collection_status`：`not_collected`、`verified` 或 `validation_failed`。执行成功但没有图片、图片损坏或疑似纯黑时，不能标记 verified。

纯黑检查只是诊断信号，先确认不是用户要求的合法全黑场景。确认异常后按下节恢复，不根据文件体积单独认定成功。现有公共收集器只记录验证失败，不自行调用服务；恢复操作由 Agent 或本模块的结果处理脚本承担。

## 黑图恢复：最多三次重启

确认异常黑图后，先检查服务队列和其他任务影响，再调用 scripts/restart_comfyui.py；重启后用 scripts/status_comfyui.py 确认就绪，并通过本模块预检，然后以新的唯一文件名前缀重投该失败任务。

同一失败任务最多执行三次恢复重启：第一次重启重投后仍黑，再执行第二次；第二次后仍黑，再执行第三次；第三次后仍黑，停止重投并告诉用户，报告参数、输出位置、日志线索和三次恢复结果。

原始失败生成不计为一次恢复重启。计数按同一逻辑任务累计，写入其记录或关联记录；新 run_id、脚本重跑或跨轮次不能把计数归零。一次恢复中若工作流本身要求投递前重启，与本次恢复重启合并执行，不重复调用。重启失败也记录本次尝试，不在服务脚本内部无限重试。

服务脚本尚未配置时，由目标电脑 Agent 按 scripts/README.md 补齐。发现其他任务冲突时先处理冲突，不为重投强清队列。需要检查输出的恢复阶段与普通异步投递轮分开；不能在收到 prompt_id 后立即重启刚入队的任务。

## 失败、恢复与重试

- 提交前失败和明确的 HTTP 4xx 拒绝记录为 `submit_failed`。
- POST 响应超时、5xx 或没有可靠任务 ID 记录为 `submission_unknown`。服务器可能已接收；先通过队列、日志和记录的 client_id 对账，不能直接重投。
- 已收到 prompt_id 但客户端在落盘前异常退出，记录可能停在 `submitting`，按同样的不确定状态处理。
- 服务历史被清理后，本地已经保存的终态与历史快照可用于重复收集；没有证据时保持未知。
- 黑图执行上述三次恢复上限；其他异常按具体模块运行规则处理。服务命令统一由 scripts 中的本机实现提供。

明确需要重试时，以原 `runs/<run_id>/task.json` 作为配置，执行 `submit --task runs/<run_id>/task.json --retry-of <run_id>`。原种子被保留，新 run 关联原 run。它使用当前工作流映射，因此也会保存新的图摘要，不能声称必然逐位复现。

图生图重试前确认原输入仍在；原文件丢失时将任务的图像参数改为该 run 的输入快照相对路径。不得凭同名新文件宣称复现了原输入。

## 收集的边界

首版只处理标准 SaveImage 的 image history，其他保存节点必须适配。只收集声明的最终输出，不把临时预览算成品。

重复 collect 会校验已收集文件，不覆盖用户修改。损坏文件也保留以便诊断。若下载或进程中断导致文件存在却无对应记录，收集器拒绝覆盖；先将该文件移动到包内 tmp 隔离，再重新 collect，不需要重新生成。

同一个 run 的 status/collect 使用排他锁。进程崩溃留下 `.operation.lock` 时，确认没有操作进程后可只移除该锁，不能清空整个 run。

公共参考运行器未实现后台轮询或服务重启；Agent 按上文执行有上限的黑图恢复。需要批量时按任务逐个提交，选择是否等待；输入去重依据长期记录中的输入摘要或图源标识，不能依赖待清理的临时文件。
