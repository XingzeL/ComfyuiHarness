# 缓冲与迭代维护

任务中的文件归属、路径、实现方式或经验结论尚不明确时，先放入包根 `buffer/`，保留原因和处理线索。缓冲区用于承接当前规则尚未覆盖的内容，并为后续版本提炼依据。

## 放什么、怎么放

每个任务或主题一个目录：`buffer/<任务或主题>/`。目录内自由组织文件，不强制分类或固定程序接口；配一份简短 README，说明：

- 暂存了什么，当前用来做什么。
- 为什么暂存，还有什么不确定。
- 已尝试的方法与结果，可引用 test 中的脚本、任务记录和日志。
- 下一步怎么处理，可能归入哪个正式位置。

候选路径也可以只记录在 README 中，不必复制相应文件。区分已确认路径与猜测，不能把未核实的路径写成已经可用的本机配置。

已有明确归属的内容仍按原规则存放：测试脚本放 test，工作流任务脚本放相应 runs，模型资料放 modelInfo/loraInfo，成图按输出规则保存；在缓冲记录中引用即可，不再复制一份。模型权重继续放本机 ComfyUI 资源目录。

## 与 tmp 的区别

tmp 放已知用途、可以重建并清理的临时中间文件。buffer 放尚待判断或有迭代价值的内容，不能按临时文件批量删除，也不能凭“已经过了几天”认定无用。

缓冲内容不是正式规则，不自动生效。实验脚本执行时仍遵守已确定的像素上限、异步投递、重启次数、文件不覆盖等规则。

## 任务收尾

每次任务结束时检查本轮新增的缓冲内容：

- 仍不确定：保留在 buffer，更新进展和下一步。
- 已明确归属：迁入对应目录，修正引用，在原记录中写明去向。
- 值得复用：按下面的迭代流程提炼。
- 仅一次性用途或已放弃：保留必要结果和原因后，归档到 archive/buffer；无保留价值的可在确认没有依赖后清理。

不要求每次任务都修改全局规则，也不要求等待暂存问题全部解决才能完成其他已明确的工作。简要汇报新增的重要未决事项及位置。

## 版本迭代

开始维护或迭代 HarnessUI 时，先查看 buffer 的未处理主题，优先处理反复出现的问题、已验证的解决方法和已确定的目录归属。

有明确依据并符合用户当前约定的内容，按用途提炼：

- 通用约定进入 docs，必要时从 AGENTS 增加阅读入口。
- 重复操作方法进入相应 Skill。
- 可复用代码或档案形式进入 templates 或正式功能目录。
- 本机路径、启动命令等进入本机配置和 scripts，不固化到跨机器规则。

合入前检查与现有规则是否冲突，按本次改动需要验证，不规定固定测试集。记录实际验证范围，未验证内容不写成通用事实。

合入后在 [变更记录](changes.md) 写明日期、变化、依据的缓冲主题和验证结果，再将已处理主题归档到 archive/buffer。归档时记录正式文件位置，方便回溯。

文件移动或清理前检查现有引用和活动任务依赖，不移动仍在使用的输入或破坏已提交任务的恢复依据。归档或整理不得覆盖已有内容。
